# Troubleshooting and Incidents

This chapter has two parts. First, a symptom-to-cause-to-fix table covering
every distinct bug encountered while building and running this stack — use
it as a lookup table if you hit something that looks familiar. Second, two
full incident narratives, written up not for the specific bug (your model,
your driver version, your Neovim config will differ) but for the
**debugging technique** each one forced, because those techniques are
reusable well outside this specific project.

Everything here reflects the exact stack pinned in
[configs/shared/versions.md](../configs/shared/versions.md). A driver
update, a llama.cpp bump, or different hardware could shift or resolve any
of these — treat the underlying reasoning as transferable and the exact
thresholds/numbers as things to re-verify on your own machine.

## 2. Incident case study: the leftover autocmd that kept killing the GPU service

### The symptom

After wiring up `gpu-server-hard` with a systemd `Conflicts=npu-server-coder.service` (so the two tiers could never run concurrently on this machine's thin memory margin — see [docs/03-gpu-tier-setup.md](03-gpu-tier-setup.md) and the concurrency findings in [docs/07-benchmarks-and-methodology.md](07-benchmarks-and-methodology.md)), the GPU tier started getting silently killed every single time a message was sent from the codecompanion chat buffer. `systemctl --user status gpu-server-hard` showed it stopped, with nothing that looked like a crash — just stopped, right around the moment a request went out.

That's the signature of `Conflicts=` doing exactly its job: something was starting `npu-server-coder`, and systemd was faithfully stopping `gpu-server-hard` in response, per the unit file's own declared relationship. The question wasn't "why did it crash" — it was "what is starting the NPU service."

### Why re-reading the edited source config wasn't enough

The obvious first move: re-open `config/nvf/nvim-config.nix` (the source file that had just been edited to remove NPU wiring from nvim in favor of the new GPU adapter) and read it end to end, looking for anything that references `npu-server-coder`. Nothing turned up. The GPU adapter block looked clean, the keymaps looked clean, the NPU-specific `http` adapter entry had genuinely been deleted.

This is the trap: **the file looked right, because the part of it that had been intentionally edited *was* right.** The bug wasn't in the section that got attention during the "remove NPU from nvim" edit — it was in a different, unrelated-looking block that nobody had reason to re-check, because nothing about it screamed "NPU" from its name or its neighboring code. nvf's `luaConfigRC` option is a Nix attribute set of independently named Lua snippets (`luaConfigRC.gpuServerWaitHelper`, `luaConfigRC.activeTheme`, and so on) — each one gets spliced into the generated Neovim config as its own chunk. An autocmd wired to codecompanion's generic `CodeCompanionRequestStarted` event, sitting under an attribute named `npuServerAutostart`, had been added earlier in the project (before the GPU tier existed) to make the NPU server start automatically whenever a chat request began. It lived in its own block, physically distant in the file from the adapter definitions that got all the editing attention, and grepping the file for the words "gpu" or "adapter" — the natural search terms for someone hunting through the section that had just changed — would never surface it, because it referenced neither.

Re-reading source more carefully, or re-reading it a second or third time, was not going to find this. The bug wasn't a mistake in the edited text; it was the *absence* of an edit somewhere the editor didn't think to look, in a part of the file with no obvious connection to what changed.

### The technique that actually found it: trace the live, compiled config, not the source you edited

The move that broke the impasse was to stop trusting a read of the source `.nix` file as ground truth for what Neovim was actually running, and instead go straight to the artifact Neovim itself loads at startup. nvf (like most Nix-based Neovim setups — nixvim included) doesn't hand Neovim your `.nix` files directly; it evaluates them at build time into one or more generated Lua files, wired together through a small bootstrap `init.lua` that `dofile()`s the real generated config out of the Nix store (visible from inside Neovim via `:echo $MYVIMRC`, and from the shell via `readlink` on that path, or by inspecting `:scriptnames` for every file actually sourced during startup). That compiled output is the one artifact guaranteed to contain *everything* currently wired into the running editor, regardless of which named source block it came from, and regardless of whether the person reading it remembers that block exists.

The concrete steps: build the generated Neovim config (`nix build` on the relevant flake output, or just start a fresh Neovim instance and resolve `$MYVIMRC`/`:scriptnames` to the real store path), then `grep` the *compiled* Lua directly for the actual event name involved in the misbehavior — `CodeCompanionRequestStarted` — rather than for a name or keyword implied by the recent edit. That search doesn't care which `luaConfigRC.*` attribute contributed which line; it surfaces every registration of that autocmd in the entire live config in one pass. That's exactly how `npuServerAutostart` turned up: not because anyone remembered its name, but because grepping the compiled output for the actual mechanism (the autocmd event) rather than the suspected culprit (the GPU adapter code) doesn't depend on already having the right hypothesis about where the bug lives.

Once found, the fix itself was trivial — delete the `luaConfigRC.npuServerAutostart` block entirely, since the on-demand `GpuStartAndOpen` keymap helper (see [configs/nvim/nvim-config.nix](../configs/nvim/nvim-config.nix)) is the only thing that should ever start a backend service now. The lesson worth carrying forward has nothing to do with codecompanion or nvf specifically:

> **When "the config I edited looks right, so why is the old behavior still happening" — stop re-reading the source you edited, and go find the actual compiled/live artifact the running system loads instead.** Then search *that* for the mechanism causing the symptom (an event name, a systemd unit name, a route path — whatever the system-level evidence points to), not for the section you assume is responsible. A live artifact doesn't care about your file's organizational boundaries; the bug you're chasing might not respect them either.

This generalizes well past Nix-based dotfiles: it's the same reason you check a compiled webpack bundle instead of just the source file you edited when a browser keeps running old JS, or check `systemctl cat` for the unit systemd actually loaded instead of the source `.nix`/`.service` file when a running daemon disagrees with its supposed config. Whenever there are two representations of "the config" — the one you write and the one the system actually executes — and they can drift or be spliced together from more places than you remember, the live one is the one to trust when your mental model of the source doesn't explain the symptom.

## 3. Incident case study: two real OOM kills, and why the fix wasn't a config change

Two separate out-of-memory kills happened over the course of this project, on two different days, from two different immediate triggers. Both are worth walking through together because they share the same underlying lesson, and because both were fully auto-recovered by `Restart=on-failure` — which is exactly what made it tempting, and wrong, to treat them as "handled" without doing anything further.

### Incident A: a second model instance, started for a quick test

While benchmarking a `-ub` (physical batch size) change against `gpu-server-hard`, the natural instinct was to spin up a second `llama-server` process on a different port pointed at the same GGUF, so the production instance could keep serving real traffic undisturbed while the test instance took the tuning experiment. On paper this looks like the safe, non-disruptive way to test — don't touch the thing that's live, stand up a parallel copy instead.

On this hardware, it isn't safe at all. `Qwen3.6-35B-A3B` at Q4_K_M plus its KV cache and speculative-decoding draft context is already a large fraction of ~30GB total system RAM for one resident copy — see the per-flag memory accounting in [configs/gpu-tier/default.nix](../configs/gpu-tier/default.nix) and the memory numbers in [docs/07-benchmarks-and-methodology.md](07-benchmarks-and-methodology.md). A second full instance does not fit alongside the first. The system dropped to 383MB free with 13/15GB of zram swap in use before the kernel's OOM killer stepped in and killed the newer process. `Restart=on-failure` on the production `gpu-server-hard` unit brought it back automatically — but the underlying resource math never had a chance of working, and no amount of automatic restart changes that math.

### Incident B: an unpaced benchmark script against the live single-parallel instance

The second kill happened during the `enable_thinking` benchmark (see [docs/04-thinking-mode-and-preservation.md](04-thinking-mode-and-preservation.md)): a first benchmarking pass fired roughly 30 requests at `gpu-server-hard` back-to-back, with no delay between them and no check on system memory state before issuing the next one. `gpu-server-hard` runs with `--parallel 1` (a deliberate choice — see [configs/gpu-tier/default.nix](../configs/gpu-tier/default.nix) — so the full context window stays on one slot instead of being split four ways), which means every one of those 30 requests queued and ran sequentially against the single production process, each a 1536-token generation. After roughly six back-to-back heavy generations with zero cooldown, the process was OOM-killed. Again, `Restart=on-failure` recovered it with no manual intervention and no config change required for the immediate outage.

### Why "it auto-recovered" is not the same as "it's fixed"

Both incidents produced the same shape of postmortem-that-isn't: the service came back up on its own, current requests eventually succeeded, and there was no data loss or corrupted state to clean up. It would have been easy to close both as non-issues on that basis. That would have been a mistake, for the same reason in both cases: **`Restart=on-failure` recovers the *process*, it does not prevent the *cause*.** Nothing about the fix that actually mattered was a change to `gpu-server-hard`'s systemd unit, its `ExecStart` flags, or the `zramSwap` configuration (already active — see [docs/07-benchmarks-and-methodology.md](07-benchmarks-and-methodology.md) — and confirmed in both cases to have been exhausted, not just present but unused headroom). Bumping `zramSwap.memoryPercent` higher would not have prevented either incident; both spikes were severe enough that a bigger number just delays the same collision, and disguises a foreseeable operator mistake as an unavoidable capacity limit.

The real fix in both cases was procedural, applied to how *testing itself* is conducted against a live production instance, not to the service being tested:

1. **Never run a second full model instance while the real one is in use.** If you need to test against the model, test against the live instance directly, or stop it first — don't stand up a parallel copy assuming it's the "safe" option. On memory-constrained hardware like this (no dedicated VRAM, one shared ~30GB pool), a second resident copy of a large model is not a lightweight isolation mechanism, it's a near-guaranteed OOM.
2. **Add a cooldown and a memory gate to any heavy benchmarking script run against a live, single-parallel production instance.** The retest that followed Incident B added a 20-second cooldown between requests and a check against `MemAvailable` (from `/proc/meminfo`) before issuing the next one, and completed the same 30-request pass cleanly with no kill. The fix is in the *benchmark harness*, not in the server it's testing.

The transferable lesson generalizes past this specific model and this specific machine: on any system where "just spin up a second copy to test in isolation" competes with the production workload for the same finite resource (RAM here, but the same reasoning applies to GPU memory, database connections, or rate-limited API quota elsewhere), automatic process-level recovery (`Restart=on-failure`, a Kubernetes liveness probe, a supervisor respawn) is a safety net for *unexpected* failures, not a substitute for **not causing a foreseeable one** through how you test. When an OOM (or any resource-exhaustion kill) auto-recovers cleanly, the follow-up question isn't "do we need to fix anything" — it's "was this a normal-usage spike we didn't anticipate, or a testing/operational pattern we created ourselves." Only the former is a signal to add capacity (bigger swap, more headroom); the latter needs a procedural fix in how the system is operated or tested, and no reasonable amount of added capacity will substitute for that.
